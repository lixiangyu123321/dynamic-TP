# JUC 阻塞队列与 DynamicTP 自定义阻塞队列实现细节
## 一、概述
Java 并发工具包（`java.util.concurrent`，简称 JUC）提供了多种标准阻塞队列实现，核心用于解决多线程环境下的生产-消费问题，保证线程安全的同时支持阻塞式的入队/出队操作。DynamicTP（动态线程池）是基于 JUC 扩展的动态线程池框架，在标准阻塞队列基础上，新增了 `VariableLinkedBlockingQueue` 和 `MemorySafeLinkedBlockingQueue` 两种自定义阻塞队列，适配动态线程池的动态扩缩容、内存安全等核心需求。

本文将详细拆解 JUC 原生 7 种阻塞队列的实现细节，以及 DynamicTP 自定义 2 种阻塞队列的设计思路、核心实现和适用场景。

## 二、JUC 原生阻塞队列实现细节
### 2.1 ArrayBlockingQueue（数组有界阻塞队列）
#### 核心定位
基于定长数组实现的**强制有界**阻塞队列，是 JUC 中最基础的阻塞队列，设计目标是内存占用可控、实现简单。

#### 底层实现
1. **存储结构**：
    - 核心数组：`final Object[] items`，初始化时必须指定容量（`capacity`），且数组长度不可变；
    - 索引指针：`int takeIndex`（消费指针）、`int putIndex`（生产指针），通过循环数组的方式实现元素的入队/出队；
    - 元素计数：`int count`，记录当前队列元素数量，避免频繁计算数组有效元素。
2. **线程安全**：
    - 独占锁：`final ReentrantLock lock`，生产和消费共用同一把锁，保证操作互斥；
    - 条件变量：`private final Condition notEmpty`（队列非空，唤醒消费线程）、`private final Condition notFull`（队列非满，唤醒生产线程）；
    - 公平性：构造函数支持 `fair` 参数（默认 `false`），公平模式下锁按 FIFO 顺序分配，避免线程饥饿，但会降低并发性能。
3. **核心方法实现**：
    - 入队（`put(E e)`）：
      ```java
      public void put(E e) throws InterruptedException {
          checkNotNull(e);
          final ReentrantLock lock = this.lock;
          lock.lockInterruptibly(); // 可中断加锁
          try {
              while (count == items.length) // 队列满则阻塞
                  notFull.await();
              enqueue(e); // 入队核心逻辑：赋值给 putIndex 位置，更新指针
          } finally {
              lock.unlock();
          }
      }
      ```
    - 出队（`take()`）：
      ```java
      public E take() throws InterruptedException {
          final ReentrantLock lock = this.lock;
          lock.lockInterruptibly();
          try {
              while (count == 0) // 队列空则阻塞
                  notEmpty.await();
              return dequeue(); // 出队核心逻辑：取 takeIndex 位置元素，更新指针
          } finally {
              lock.unlock();
          }
      }
      ```

#### 核心特点
| 维度         | 详情                                                                 |
|--------------|----------------------------------------------------------------------|
| 有界性       | 强制有界，初始化必须指定容量，无扩容机制                             |
| 排序规则     | 严格 FIFO（先进先出）                                                |
| 并发性能     | 一般（生产/消费共用一把锁，无法并行）                               |
| 内存占用     | 固定内存（数组容量），无额外开销                                     |
| 异常处理     | 队列满时 `add()` 抛 `IllegalStateException`，`put()` 阻塞，`offer()` 返回 `false` |

#### 适用场景
- 严格控制队列容量、内存占用可预估的场景（如固定大小的任务缓冲池）；
- 生产/消费速率相对均衡，无需高并发的简单场景。

### 2.2 LinkedBlockingQueue（链表可选界阻塞队列）
#### 核心定位
基于单向链表实现的**可选界**阻塞队列，是 JUC 中最常用的阻塞队列，平衡了并发性能和灵活性。

#### 底层实现
1. **存储结构**：
    - 链表节点：`static class Node<E> { E item; Node<E> next; }`，单向链表节点，动态创建；
    - 头尾指针：`transient Node<E> head`（头节点，空节点占位）、`transient Node<E> last`（尾节点）；
    - 容量控制：`private final int capacity`（默认 `Integer.MAX_VALUE`，即无界），`private final AtomicInteger count = new AtomicInteger()`（原子计数，避免锁竞争）。
2. **线程安全**：
    - 双锁分离：`private final ReentrantLock takeLock`（消费锁）、`private final ReentrantLock putLock`（生产锁），生产和消费使用独立锁，支持并行操作；
    - 条件变量：`private final Condition notEmpty`（消费条件）、`private final Condition notFull`（生产条件）；
    - 锁粒度：仅在修改头尾指针/计数时加锁，迭代器遍历无需加锁（弱一致性）。
3. **核心方法实现**：
    - 入队（`put(E e)`）：
      ```java
      public void put(E e) throws InterruptedException {
          if (e == null) throw new NullPointerException();
          int c = -1;
          Node<E> node = new Node<E>(e);
          final ReentrantLock putLock = this.putLock;
          final AtomicInteger count = this.count;
          putLock.lockInterruptibly();
          try {
              while (count.get() == capacity) // 队列满则阻塞
                  notFull.await();
              enqueue(node); // 尾插法入队
              c = count.getAndIncrement();
              if (c + 1 < capacity) // 队列仍有空间，唤醒其他生产线程
                  notFull.signal();
          } finally {
              putLock.unlock();
          }
          if (c == 0) // 入队前队列为空，唤醒消费线程
              signalNotEmpty();
      }
      ```
    - 出队（`take()`）：消费锁独立加锁，逻辑与入队对称，核心是头节点出队并更新计数。

#### 核心特点
| 维度         | 详情                                                                 |
|--------------|----------------------------------------------------------------------|
| 有界性       | 可选界（默认无界），指定容量则为有界，无扩容机制                     |
| 排序规则     | 严格 FIFO                                                            |
| 并发性能     | 较高（生产/消费并行，双锁分离）                                     |
| 内存占用     | 动态内存（链表节点），无界模式下可能导致 OOM                         |
| 迭代性能     | 高（弱一致性迭代器，无需加锁）                                       |

#### 适用场景
- 通用线程池任务队列（如 `FixedThreadPool` 默认队列）；
- 任务量不可预估、需要高并发生产/消费的场景；
- 需频繁遍历队列元素的场景。

### 2.3 PriorityBlockingQueue（优先级无界阻塞队列）
#### 核心定位
基于可扩容数组实现的**无界优先级**阻塞队列，核心是按优先级排序而非 FIFO。

#### 底层实现
1. **存储结构**：
    - 堆数组：`private transient Object[] queue`，底层是二叉最小堆（默认自然序），支持自定义 `Comparator`；
    - 容量扩容：默认初始容量 11，满时自动扩容（`int newCapacity = oldCapacity + (oldCapacity < 64 ? (oldCapacity + 2) : (oldCapacity >> 1))`）；
    - 原子计数：`private final AtomicInteger size = new AtomicInteger()`。
2. **线程安全**：
    - 独占锁：`private final ReentrantLock lock`，生产/消费共用一把锁；
    - 条件变量：`private final Condition notEmpty`（仅消费阻塞，无生产阻塞，因为无界）；
    - 无满队列状态：生产永不阻塞，仅消费在队列为空时阻塞。
3. **核心逻辑**：
    - 入队：通过堆化（`siftUp`）保证新元素插入后仍为最小堆；
    - 出队：取出堆顶元素后，通过堆化（`siftDown`）维持堆结构；
    - 优先级：同优先级元素的顺序不保证（堆排序特性）。

#### 核心特点
| 维度         | 详情                                                                 |
|--------------|----------------------------------------------------------------------|
| 有界性       | 无界（受内存限制），自动扩容                                         |
| 排序规则     | 优先级排序（默认自然序，支持自定义 Comparator）                     |
| 并发性能     | 一般（独占锁），扩容时会加锁复制数组，性能下降                       |
| 特殊限制     | 元素必须实现 `Comparable` 或自定义 Comparator，否则抛 `ClassCastException` |

#### 适用场景
- 按优先级处理任务的场景（如紧急任务优先执行、定时任务排序）；
- 无需控制队列容量，且任务有明确优先级的场景。

### 2.4 DelayQueue（延迟无界阻塞队列）
#### 核心定位
基于 `PriorityBlockingQueue` 扩展的**延迟执行**无界阻塞队列，仅当元素延迟时间到期后才可被消费。

#### 底层实现
1. **存储结构**：
    - 底层依赖：`private final PriorityQueue<E> q = new PriorityQueue<E>()`（实际是 `PriorityBlockingQueue`）；
    - 元素要求：必须实现 `Delayed` 接口，重写 `long getDelay(TimeUnit unit)`（剩余延迟时间）和 `int compareTo(Delayed o)`（按延迟时间排序）。
2. **核心机制**：
    - 延迟判断：消费时仅当 `getDelay(TimeUnit.NANOSECONDS) <= 0` 时，元素才可被取出；
    - 阻塞逻辑：`take()` 方法会阻塞直到有元素延迟到期，或等待期间被中断。
3. **核心方法实现**：
   ```java
   public E take() throws InterruptedException {
       final ReentrantLock lock = this.lock;
       lock.lockInterruptibly();
       try {
           for (;;) {
               E first = q.peek();
               if (first == null)
                   available.await(); // 队列为空，阻塞
               else {
                   long delay = first.getDelay(NANOSECONDS);
                   if (delay <= 0)
                       return q.poll(); // 延迟到期，出队
                   first = null; // 避免内存泄漏
                   if (leader != null)
                       available.await(); // 已有线程等待，当前线程阻塞
                   else {
                       Thread thisThread = Thread.currentThread();
                       leader = thisThread;
                       try {
                           available.awaitNanos(delay); // 等待延迟时间到期
                       } finally {
                           if (leader == thisThread)
                               leader = null;
                       }
                   }
               }
           }
       } finally {
           if (leader == null && q.peek() != null)
               available.signal(); // 唤醒下一个等待线程
           lock.unlock();
       }
   }
   ```

#### 核心特点
| 维度         | 详情                                                                 |
|--------------|----------------------------------------------------------------------|
| 有界性       | 无界（受内存限制）                                                   |
| 排序规则     | 按延迟时间升序（延迟时间越短，优先级越高）                           |
| 消费规则     | 仅延迟到期的元素可被消费，未到期元素无法获取                         |
| 并发性能     | 同 PriorityBlockingQueue（一般）                                     |

#### 适用场景
- 定时任务调度（如 `ScheduledThreadPoolExecutor` 的任务队列）；
- 延迟通知、缓存过期清理、订单超时关闭等场景。

### 2.5 SynchronousQueue（同步阻塞队列）
#### 核心定位
**零容量**的同步阻塞队列，无底层存储结构，生产操作必须等待消费操作，消费操作必须等待生产操作（“一手交钱一手交货”）。

#### 底层实现
1. **存储结构**：无存储数组/链表，仅维护生产/消费线程的匹配关系；
2. **实现模式**：
    - 公平模式：基于 `TransferQueue`（队列）实现，按 FIFO 顺序匹配线程；
    - 非公平模式：基于 `TransferStack`（栈）实现，默认模式，匹配效率更高；
3. **核心机制**：
    - 转移逻辑：`transfer(E e, boolean timed, long nanos)` 方法是核心，生产线程传入元素，阻塞直到消费线程取走；消费线程阻塞直到生产线程传入元素；
    - 无存储开销：元素直接从生产线程传递到消费线程，无中间存储。

#### 核心特点
| 维度         | 详情                                                                 |
|--------------|----------------------------------------------------------------------|
| 有界性       | 零容量（无存储）                                                     |
| 排序规则     | 公平模式 FIFO，非公平模式随机                                       |
| 并发性能     | 极高（无存储开销，CAS 实现无锁匹配）                                 |
| 阻塞规则     | 生产/消费互相阻塞，无元素可存储                                     |

#### 适用场景
- 生产消费严格同步、任务需立即执行的场景（如 `CachedThreadPool` 默认队列）；
- 高并发短任务场景，无需缓存任务，直接传递给消费线程。

### 2.6 LinkedTransferQueue（链表转移无界阻塞队列）
#### 核心定位
基于单向链表实现的**无界转移**阻塞队列，继承 `SynchronousQueue` 的转移特性，同时扩展了存储能力。

#### 底层实现
1. **存储结构**：
    - 链表节点：`static final class Node`，支持三种状态（数据节点、请求节点、匹配节点）；
    - 无锁实现：基于 CAS + 自旋实现无锁并发，避免传统锁的开销。
2. **核心方法**：
    - `transfer(E e)`：生产线程阻塞直到元素被消费（同步转移）；
    - `tryTransfer(E e)`：非阻塞转移，立即返回是否匹配到消费线程；
    - `tryTransfer(E e, long timeout, TimeUnit unit)`：超时阻塞转移；
    - `put(E e)`：无阻塞入队（异步转移），元素存入队列，等待消费。
3. **核心优势**：
    - 兼容 `SynchronousQueue` 的同步转移和 `LinkedBlockingQueue` 的异步入队；
    - 无锁设计，并发性能远超传统阻塞队列。

#### 核心特点
| 维度         | 详情                                                                 |
|--------------|----------------------------------------------------------------------|
| 有界性       | 无界（受内存限制）                                                   |
| 排序规则     | FIFO                                                                 |
| 并发性能     | 最高（CAS 无锁 + 自旋，无锁竞争）                                   |
| 特殊能力     | 支持同步/异步/超时转移，灵活适配不同生产消费策略                     |

#### 适用场景
- 高性能 RPC 框架的消息队列；
- 高并发生产消费场景，需灵活控制元素转移策略（同步/异步）。

### 2.7 LinkedBlockingDeque（链表双向阻塞队列）
#### 核心定位
基于双向链表实现的**可选界**双向阻塞队列，支持从队列头部/尾部入队/出队，可作为栈或队列使用。

#### 底层实现
1. **存储结构**：
    - 双向链表节点：`static final class Node<E> { E item; Node<E> prev; Node<E> next; }`；
    - 头尾指针：`transient Node<E> first`、`transient Node<E> last`；
    - 容量控制：`private final int capacity`（默认 `Integer.MAX_VALUE`），`private final AtomicInteger count = new AtomicInteger()`。
2. **线程安全**：
    - 双锁分离：`private final ReentrantLock lock = new ReentrantLock()`（统一锁，JDK 8 后优化为头尾独立锁）；
    - 条件变量：`private final Condition notEmpty`、`private final Condition notFull`；
3. **核心方法**：
    - 头入队：`addFirst(E e)`、`putFirst(E e)`；
    - 尾入队：`addLast(E e)`、`putLast(E e)`；
    - 头出队：`takeFirst()`；
    - 尾出队：`takeLast()`。

#### 核心特点
| 维度         | 详情                                                                 |
|--------------|----------------------------------------------------------------------|
| 有界性       | 可选界（默认无界）                                                   |
| 排序规则     | FIFO（队列模式）/ FILO（栈模式）                                     |
| 并发性能     | 较高（头尾独立锁，支持并行操作）                                     |
| 特殊能力     | 双向操作，可作为栈/队列使用                                         |

#### 适用场景
- 需要双向操作队列的场景（如任务队列头尾都可消费、生产者插队到队首）；
- 需实现栈结构的并发场景。

## 三、DynamicTP 自定义阻塞队列实现细节
DynamicTP 是基于 JUC 扩展的动态线程池框架，核心解决线程池参数动态调整、监控告警、内存安全等问题。其自定义的 `VariableLinkedBlockingQueue` 和 `MemorySafeLinkedBlockingQueue` 均基于 `LinkedBlockingQueue` 扩展，适配动态线程池的核心需求。

### 3.1 VariableLinkedBlockingQueue（动态容量链表阻塞队列）
#### 设计背景
JUC 原生 `LinkedBlockingQueue` 的容量一旦指定不可修改，而动态线程池需要根据业务负载动态调整队列容量（如高峰期扩容队列，低谷期缩容），因此扩展出支持动态调整容量的 `VariableLinkedBlockingQueue`。

#### 核心实现
1. **核心改造点**：
    - 容量动态化：将原 `final int capacity` 改为可修改的 `AtomicInteger` 类型，提供 `setCapacity(int newCapacity)` 方法；
    - 扩容逻辑：扩容时无需迁移元素，仅修改容量阈值，入队时判断新容量是否允许；
    - 缩容逻辑：缩容时若当前元素数超过新容量，阻塞生产线程直到元素消费至新容量以下。
2. **核心代码**：
   ```java
   public class VariableLinkedBlockingQueue<E> extends LinkedBlockingQueue<E> {
       // 动态容量，原子更新保证线程安全
       private final AtomicInteger dynamicCapacity;
       
       public VariableLinkedBlockingQueue(int initialCapacity) {
           super(initialCapacity);
           this.dynamicCapacity = new AtomicInteger(initialCapacity);
       }
       
       // 动态设置容量
       public void setCapacity(int newCapacity) {
           if (newCapacity <= 0) {
               throw new IllegalArgumentException("Capacity must be positive");
           }
           dynamicCapacity.set(newCapacity);
           // 缩容时唤醒消费线程，加速元素消费
           this.signalNotEmpty();
       }
       
       // 重写入队判断逻辑，使用动态容量
       @Override
       public void put(E e) throws InterruptedException {
           if (e == null) throw new NullPointerException();
           int c = -1;
           Node<E> node = new Node<E>(e);
           final ReentrantLock putLock = this.putLock;
           final AtomicInteger count = this.count;
           putLock.lockInterruptibly();
           try {
               // 核心修改：使用 dynamicCapacity 替代原固定容量
               while (count.get() >= dynamicCapacity.get()) {
                   notFull.await();
               }
               enqueue(node);
               c = count.getAndIncrement();
               if (c + 1 < dynamicCapacity.get()) {
                   notFull.signal();
               }
           } finally {
               putLock.unlock();
           }
           if (c == 0) {
               signalNotEmpty();
           }
       }
   }
   ```
3. **核心特点**：
   | 维度         | 详情                                                                 |
   |--------------|----------------------------------------------------------------------|
   | 有界性       | 动态有界，支持运行时调整容量                                         |
   | 兼容特性     | 完全兼容 LinkedBlockingQueue 的所有方法，无侵入式改造               |
   | 线程安全     | 原子类保证容量修改线程安全，缩容时阻塞生产，避免数据丢失             |
   | 性能影响     | 扩容无性能损耗，缩容可能阻塞生产（可控）                             |

#### 适用场景
- 动态线程池的任务队列，需根据业务负载调整队列容量；
- 流量波动大的场景（如秒杀、营销活动），高峰期扩容队列，低谷期缩容节省内存。

### 3.2 MemorySafeLinkedBlockingQueue（内存安全链表阻塞队列）
#### 设计背景
JUC 原生 `LinkedBlockingQueue` 无界模式下可能因任务堆积导致 OOM（内存溢出），而动态线程池需要保证内存安全，因此扩展出基于内存阈值控制的 `MemorySafeLinkedBlockingQueue`。

#### 核心实现
1. **核心设计思路**：
    - 内存阈值：设置队列占用内存的上限（如 1GB），而非元素数量；
    - 内存计算：统计每个入队元素的内存占用（基于对象大小估算），累计队列总内存；
    - 阻塞策略：当队列总内存超过阈值时，阻塞生产线程，直到消费释放内存。
2. **核心改造点**：
    - 内存统计：`private final AtomicLong totalMemory = new AtomicLong(0)`，记录队列总内存；
    - 内存阈值：`private final long memoryThreshold`，初始化时指定；
    - 元素内存估算：提供 `estimateMemorySize(E e)` 方法，默认基于对象序列化大小估算，支持自定义；
    - 入队拦截：入队前检查总内存是否超过阈值，超过则阻塞。
3. **核心代码**：
   ```java
   public class MemorySafeLinkedBlockingQueue<E> extends LinkedBlockingQueue<E> {
       // 内存阈值（字节）
       private final long memoryThreshold;
       // 队列总内存占用（原子更新）
       private final AtomicLong totalMemory = new AtomicLong(0);
       
       public MemorySafeLinkedBlockingQueue(long memoryThreshold) {
           super(Integer.MAX_VALUE); // 底层无界，通过内存控制
           this.memoryThreshold = memoryThreshold;
       }
       
       // 估算单个元素的内存占用（默认实现，可重写）
       protected long estimateMemorySize(E e) {
           if (e == null) return 0;
           // 基于序列化估算对象大小，简化实现
           try (ByteArrayOutputStream bos = new ByteArrayOutputStream();
                ObjectOutputStream oos = new ObjectOutputStream(bos)) {
               oos.writeObject(e);
               return bos.size();
           } catch (IOException ex) {
               return 1024; // 默认 1KB
           }
       }
       
       @Override
       public void put(E e) throws InterruptedException {
           if (e == null) throw new NullPointerException();
           // 估算元素内存
           long elemMemory = estimateMemorySize(e);
           int c = -1;
           Node<E> node = new Node<E>(e);
           final ReentrantLock putLock = this.putLock;
           final AtomicInteger count = this.count;
           putLock.lockInterruptibly();
           try {
               // 核心逻辑：内存超过阈值则阻塞
               while (totalMemory.get() + elemMemory > memoryThreshold) {
                   notFull.await();
               }
               enqueue(node);
               // 更新总内存和计数
               totalMemory.addAndGet(elemMemory);
               c = count.getAndIncrement();
               if (totalMemory.get() + elemMemory < memoryThreshold) {
                   notFull.signal();
               }
           } finally {
               putLock.unlock();
           }
           if (c == 0) {
               signalNotEmpty();
           }
       }
       
       @Override
       public E take() throws InterruptedException {
           final ReentrantLock takeLock = this.takeLock;
           takeLock.lockInterruptibly();
           try {
               while (count.get() == 0) {
                   notEmpty.await();
               }
               E e = dequeue();
               // 消费后减少总内存
               long elemMemory = estimateMemorySize(e);
               totalMemory.addAndGet(-elemMemory);
               // 唤醒生产线程
               if (totalMemory.get() < memoryThreshold) {
                   signalNotFull();
               }
               return e;
           } finally {
               takeLock.unlock();
           }
       }
   }
   ```
4. **核心特点**：
   | 维度         | 详情                                                                 |
   |--------------|----------------------------------------------------------------------|
   | 控制维度     | 基于内存占用控制，而非元素数量，更贴合实际内存使用场景               |
   | 内存安全     | 严格限制队列总内存，避免 OOM                                         |
   | 灵活性       | 支持自定义元素内存估算逻辑，适配不同类型任务                         |
   | 性能影响     | 元素内存估算有轻微开销（可优化为缓存估算结果）                       |

#### 适用场景
- 内存敏感的场景，需严格控制队列内存占用（如容器化部署、低内存服务器）；
- 任务大小差异大的场景（如小任务和大文件任务混合），按内存控制比按数量控制更合理；
- 动态线程池的核心队列，保证服务内存稳定性。

## 四、核心对比总结
### 4.1 JUC 原生阻塞队列对比
| 队列类型                | 存储结构       | 有界性         | 核心特性                          | 并发性能 | 典型应用场景                  |
|-------------------------|----------------|----------------|-----------------------------------|----------|-------------------------------|
| ArrayBlockingQueue      | 定长数组       | 强制有界       | 独占锁、FIFO、公平/非公平锁       | 一般     | 固定容量任务缓冲池            |
| LinkedBlockingQueue     | 单向链表       | 可选界（默认无界） | 双锁分离、FIFO、迭代效率高        | 较高     | 通用线程池任务队列            |
| PriorityBlockingQueue   | 可扩容数组     | 无界           | 优先级排序、无满队列状态          | 一般     | 按优先级执行任务              |
| DelayQueue              | 优先级队列     | 无界           | 延迟到期消费、仅处理到期元素      | 一般     | 定时任务、缓存过期清理        |
| SynchronousQueue        | 无存储结构     | 零容量         | 生产消费同步、无存储开销          | 极高     | 任务需立即执行的场景          |
| LinkedTransferQueue     | 单向链表       | 无界           | CAS 无锁、支持 transfer 方法      | 最高     | 高性能 RPC 消息队列           |
| LinkedBlockingDeque     | 双向链表       | 可选界（默认无界） | 双向操作、双锁分离、可作为栈/队列 | 较高     | 需头尾操作的队列场景          |

### 4.2 DynamicTP 自定义队列 vs JUC 原生队列
| 队列类型                     | 基于哪个 JUC 队列扩展 | 核心差异                     | 解决的核心问题                 |
|------------------------------|-----------------------|------------------------------|--------------------------------|
| VariableLinkedBlockingQueue  | LinkedBlockingQueue   | 支持动态调整容量             | 动态线程池队列容量动态扩缩容   |
| MemorySafeLinkedBlockingQueue| LinkedBlockingQueue   | 基于内存阈值控制队列         | 避免无界队列导致的 OOM         |

## 五、选型建议
1. **通用场景**：优先选择 `LinkedBlockingQueue`（平衡性能和灵活性）；
2. **容量严格可控**：选择 `ArrayBlockingQueue`；
3. **优先级任务**：选择 `PriorityBlockingQueue`；
4. **定时任务**：选择 `DelayQueue`；
5. **高并发即时任务**：选择 `SynchronousQueue` 或 `LinkedTransferQueue`；
6. **双向操作场景**：选择 `LinkedBlockingDeque`；
7. **动态线程池场景**：
    - 流量波动大：选择 `VariableLinkedBlockingQueue`；
    - 内存敏感：选择 `MemorySafeLinkedBlockingQueue`。

## 六、关键细节补充
1. **阻塞队列的阻塞策略**：
    - `put()`/`take()`：无限阻塞，直到队列可用；
    - `offer()`/`poll()`：非阻塞，立即返回是否成功；
    - `offer(timeout)`/`poll(timeout)`：超时阻塞，超时后返回；
2. **内存安全注意事项**：
    - 无界队列（如 `LinkedBlockingQueue` 默认）必须配合内存监控，避免 OOM；
    - `MemorySafeLinkedBlockingQueue` 的内存估算逻辑可优化（如基于 JOL 工具精准计算对象大小）；
3. **动态线程池适配**：
    - DynamicTP 自定义队列完全兼容 JUC 线程池，可直接替换原生队列；
    - 动态调整容量时，建议配合线程池核心线程数/最大线程数调整，达到最佳负载。
